Foundry VTT · LANCER · SillyTavern

NHP Uplink Signal Path

Foundry and SillyTavern cannot talk to each other directly. Three pieces carry the loop: a Foundry module that watches the fight, a SillyTavern server plugin that holds two separate HTTP faces, and a SillyTavern UI extension that feeds the character card and relays its reply back to the table.

The relay figure 1

One dice roll in Foundry becomes one paragraph of fiction in Foundry chat. The loop crosses two process boundaries and one origin boundary on the way out, and the same two coming back — every hop below is a real HTTP call.

Do not point Foundry at SillyTavern’s web UI port. The uplink URL is the :5088 listener — a different socket in the same process. Pointing Foundry at SillyTavern’s own port is the most common misconfiguration, and it fails as a blocked CORS preflight before the POST is ever sent.

One attack, end to end sequence

  1. Foundry fires a hook

    uplink.js listens on lancer.postFlow.* for attacks, tech attacks, damage, structure and stress, plus actor, token and effect updates. The rendered chat card is folded into the flow event that produced it, so one attack is one line, not two.

  2. Events batch, then flush

    Nothing is sent per-hook. Events collect for a 450ms debounce — just long enough for a flow and its chat card to leave together — then go out with a fresh board-state snapshot. The 2.5-second quiet period comes later, in the UI extension (step 5). Only the primary active GM’s client transmits, so a second GM at the table does not duplicate the feed.

  3. POST /event to port 5088

    Cross-origin, carrying X-Uplink-Key. The plugin appends to its inbound queue and broadcasts to every connected stream. It stamps its own receive time and sequence over whatever the sender supplied, and the snapshot replaces the stored one only if it belongs to the same world and is not older than what is already held — otherwise the previous state stands and the payload is recorded as a conflict.

  4. Server-sent events push it to the browser

    The UI extension holds an EventSource on /stream and tracks a sequence cursor, so a dropped connection resumes rather than replays.

  5. The extension writes into the chat

    Arriving events are held until the table has been quiet for 2.5 seconds (never longer than 15), then built into one digest. The digest is pushed into the chat as a message — as you, or as the narrator, depending on settings — while the board state goes in separately through setExtensionPrompt(), so the log holds one snapshot rather than accumulating stale copies. That snapshot is labelled with its source world, the time it was taken and how old it now is; the age is recomputed every second, so it decays into STALE on its own when Foundry goes quiet or the stream drops.

  6. Generation, if the gate opens

    In auto mode the extension calls /trigger, but only past a cooldown or an unnarrated backlog, so a flurry of rolls becomes one reply. manual injects and waits for you; observe logs the digest to the console and stops there. SillyTavern handles the model call — KoboldCpp or any other connector.

  7. The reply is relayed back

    MESSAGE_RECEIVED fires, the extension skips anything it injected itself, and POST /narration puts the text on the plugin’s outbound queue.

  8. Foundry polls and posts

    GET /outbound?since= runs on the module’s poll interval. Each item becomes a ChatMessage under the configured speaker alias, flagged so the module never re-ingests its own narration.

Wire reference routes & auth

Route Served on Called by Carries
POST /event standalone :5088 Foundry module event batch + board state
GET /outbound?since= standalone :5088 Foundry module queued narration, cursor
GET /stream ST plugin router UI extension SSE: hello, events, state
POST /narration ST plugin router UI extension reply text + speaker
GET /state, /inbound ST plugin router UI extension board state + freshness label, backlog
GET /status, POST /clear ST plugin router UI extension health, queue reset

POST /event and GET /outbound carry X-Uplink-Key, matched against secret in the plugin’s config.json. Two :5088 exceptions answer without it: CORS preflights (OPTIONS) and GET /health, which reports only queue sizes and last contact. The ST plugin router routes never check the secret; they sit behind SillyTavern’s own session and CSRF middleware. A blank secret disables the check entirely and the plugin logs auth: OFF at startup. The listener binds 127.0.0.1, but the secret still matters: any page you visit can attempt requests to localhost, and CORS here has to be permissive because Foundry’s origin varies by deployment.

Off the relay optional pieces

KoboldCpp and other backends

The uplink has no model configuration and never calls a backend. It hands SillyTavern text; whatever connector SillyTavern is set to — KoboldCpp on the same machine, a hosted API — is entirely SillyTavern’s business.

ComfyUI and TTS

Both are SillyTavern’s own extensions working from the same chat. They illustrate and voice the AI GM without the uplink participating in any way, which is exactly why they keep working out of combat when no events are flowing.

Lancer // CompCon theme

Cosmetic and separate: a SillyTavern theme in COMP/CON’s palette that colour-codes who is speaking. Its own repository, installed independently, no effect on the relay.

Import GUI — a second, unrelated track

The Lancer NPC Import GUI also ships its Foundry half in this module (scripts/importer.js), which makes it easy to mistake for part of the relay. It is not. It shares no endpoint, no port and no process, and works whether or not SillyTavern is installed.
